## Credential design implemented in source

- OP-TEE TA source: `mobile/systemui/tee/credential_ta/credential_ta.c`.
- C++ transport/backend: `mobile/systemui/runtime/src/TeeCredentialBackend.cpp`.
- Owning runtime wrapper: `TeeCredentialService`.
- Shared command protocol: `mobile/systemui/tee/include/fahim_credential_protocol.h`.
- The TA accepts numeric PINs of 4–16 digits (production recommendation: 6+ digits).
- It generates a random 256-bit salt and a TEE-held HMAC-SHA256 pepper key during enrollment. Only the salted HMAC verifier, format metadata, failed-attempt count, lockout level, retry deadline and last-seen secure time are stored; the raw PIN is not stored.
- Credential and pepper objects use `TEE_STORAGE_PRIVATE_RPMB`.
- The TA requires `gpd.tee.trustedStorage.antiRollback.protectionLevel >= 1000` and `gpd.tee.systemTime.protectionLevel >= 1000`. Missing/weak capability, storage errors, clock rollback, malformed records or missing pepper fail closed.
- Five failures trigger persistent escalating lockout (30 seconds upward, capped at one hour); success resets the failure and escalation state.
- The TA creates the pepper only during enrollment; verification never silently recreates a missing pepper.

## Explicitly not yet production-integrated

- No OP-TEE Secure World/BL32 is deployed or launched by Fahim OS's current boot chain.
- No device RPMB key, RPMB secure storage backend or TEE-protected system clock has been provisioned or tested on physical hardware.
- No production TA signing key/trust anchor is configured. The CI key is development-only.
- Enrollment is accepted only from a separately signed TEE Trusted Application with pinned UUID `28e3b2d4-4a20-4f91-9a11-464148494d50`. That provisioning TA and its Trusted UI/physical-presence flow are not implemented here. Therefore first-time credential enrollment is intentionally unavailable to the public TEEC client.
- The native runtime is not boot-launched as a trusted Lock Screen service. The kernel QEMU role-gate test uses a synthetic LOCKSCREEN-role payload; it does not boot the native renderer or verify a real PIN.
- The runner's TEEC-enabled tests have no TEE hardware. Passing them proves the client branch compiles/links and unavailable hardware fails closed; it does not prove secure-world invocation on a device.
